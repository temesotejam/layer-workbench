# Experimental deterministic sparse-infill arc sorting (v2.5.0)

The same-archive comparison in [run 45662478220](https://github.com/temesotejam/layer-workbench/actions/runs/45662478220) measured sparse unmatched length per engine of 4091.04 mm (baseline), 3798.00 mm (single-ended anchor disabled), and **0 mm** (both anchor settings zero). The last control had 1820 line groups, 23179.888011 mm shared sparse coverage, and 5724 extrusion moves in each engine. Strict ordered G-code still failed in all three conditions. This supports investigating the boundary connector, not disabling anchors as a production fix.

Pinned [FillBase.cpp](https://github.com/OrcaSlicer/OrcaSlicer/blob/40ecc66f78ed72dc368e0c1ebe40d77f00cc8a19/src/libslic3r/Fill/FillBase.cpp#L1857) sorts arcs by length alone in the first pass, and later accepts an alternate contour ordering only if the predicted join count strictly improves. Equal lengths can therefore choose different connections without changing the total count. This is a source-based hypothesis, not proof of a native/WASM standard-library difference.

The isolated patch candidate keeps non-tied primary length ordering and secondary bucket/contour/direction ordering, then adds contour/parameter/endpoint-index tie breaks. Endpoint index is derived from the same graph array, not pointer address ordering. This assumes finite geometry and stable graph identity; near ties, graph construction order, and official CLI's particular choices remain unverified. The proposed order may alter native behavior too, so it must not replace the accepted engine without real comparison.

The dedicated CI job downloads the pinned upstream file only into a disposable runner, validates its Git blob hash, changes exactly two sort sites and compiles the same candidate lambdas in a synthetic permutation regression using GCC and Emscripten 3.1.74. Source is kept under upstream [AGPL-3.0](https://github.com/OrcaSlicer/OrcaSlicer/blob/40ecc66f78ed72dc368e0c1ebe40d77f00cc8a19/LICENSE.txt); no full upstream source is committed or redistributed here. This is a candidate staging and comparator test only. It does not compile the full FillBase.cpp or test real geometry. If both toolchains pass, next stage is an explicitly experimental engine build with a separate artifact and the unmodified strict baseline comparison. No new production settings, artifact promotion, Pages activation, or printability claim.


## 2026-11-26: isolated full-engine experiment

The [exact comparator probe (45675583842)](https://github.com/temesotejam/layer-workbench/actions/runs/45675583842) passed its native GCC and Emscripten gates. The new PR-only `experiment-v250-infill-arc-engine.yml` builds the exact recipe and workspace from accepted artifact run 45284215349 (`f2b3c08bdc97ca551df924e82a2d5929f35654fe`), adding only the staged two-sort patch to the pinned OrcaSlicer source. It checks the upstream SHA and verifies the staged file digest after compilation; accepted compiler caches are read but not updated. Existing build, binding, conformance, smoke and 3MF gates remain in the experimental job. Its differently named artifact expires after one day and is only consumed by the dependent job in the same run; no production workflow or accepted artifact selection is changed.

The second job checks out the already tested same-archive fixture at `c4ff91c2c8bcccdb5818cc56087cb22509e1005e`, obtains the original accepted artifact and creates/validates the source-preserving native project using that artifact. It slices the same unchanged archive using official v2.5.0, the accepted engine and the experimental engine with the original nonzero anchor settings. Archive digest and identical serialized WASM config maps are required. It logs bounded numeric strict comparison and sparse coverage metrics for all three pairings; the experimental vs official strict comparator remains a failing gate if commands differ. A difference in geometry may be useful evidence without full parity. No raw G-code, 3MF, upstream presets or candidate artifact are deployed to Pages. Results are pending the new CI run.
